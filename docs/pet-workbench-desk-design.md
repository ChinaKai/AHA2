## 一、结论

宠物工作台的概览页现在按数据类型摆：一行宠物状态、三张数字卡（待审批、关注异常、渠道异常）、关注列表、最近动态。owner 打开它，看到的是几个数字，要自己点进去拼出“现在有什么事等我”。

改造后，概览页按“谁该动”来摆，从上到下四块：

1. **要你定**：不处理就有任务停着的事。
2. **等别人**：已经在动、不需要你的事。
3. **在跑什么**：正在执行的任务和它占用的硬件。
4. **宠物这边**：你最近否决并写了原因的决定、宠物的未闭环清单和议程。

这四块用的全部是 AHA 已经存着的状态，没有新造一套数据。本次补了三处缺口，让页面和宠物都能读到它们（见第五节）。

## 二、要解决的问题

owner 的原话是“宠物在 AHA 正是这个角色”。课上那张 “Two Loops, One Brain” 的图把这个角色讲成三件事，对应到 AHA：

- **分诊**：事情进来先分流，能直接办的交给 Agent，要定方向的才找人。
- **守住决策漏斗**：一个决定先看知识里有没有答案，再看能不能用确定性检查解决，再看 Agent 能不能自己定，最后才到人。
- **养知识**：维护所有 Agent 共用的那份判断依据。

宠物现在已经在做前两件事：被事件唤醒、跟踪未闭环任务、把真正要 owner 定的事提成审批。问题在于 owner 这一侧看不到它做的结果。核对代码后有三个具体缺口：

1. **宠物知道的比工作台显示的多。** 宠物每次唤醒读的工作状态里有：每个未闭环任务为什么要关注、哪个任务在评审中、未闭环清单、议程、owner 的纠正记录。工作台接口只返回文档、审批、关注列表、渠道和一个汇总数字。
2. **任务自己写的“等 owner 决定的事”没人汇总。** 每个 Task 每轮结束都会更新状态卡，里面有一栏专门写等 owner 决定什么。工作台不读它，宠物的任务详情工具也不返回它。owner 要一个个任务点进去看。
3. **“等你”和“不等你”混在一起。** 一个任务停在等待状态，可能是在等你决定，可能只是上一轮做完了等你下一句话，也可能在等评审。现在的关注列表只显示状态，三种情况长得一样。

## 三、约束

- owner 定的原则（2026-11-26）：参考图只借思路，实施必须是 AHA 自己的东西，不照搬。
- 不新增表，不新增需要 Agent 额外填写的字段。页面上的每一项都要能说清是从哪条已有记录算出来的。
- 工作台接口服务端有 10 秒上限，页面 12 秒超时。新增的数据不能让查询次数随任务数增长。
- 新数据读取失败时，工作台其余部分照常可用。
- 忽略名单继续生效：owner 忽略的任务不出现在工位上。

## 四、设计

### 4.1 页面结构

工作台仍是四个页签：概览、审批、记录、设置。只改概览。

```
┌──────────────────────────────────────────────────────────────────────┐
│ 宠物状态：正常 · 3 件要你定 · 2 件等别人 · 4 个在跑      巡检 09:40  │
├──────────────────────────────────────────────────────────────────────┤
│ 要你定（3）                                    不急的还有 12 件  ▸   │
│ ① task-790 被阻塞 · 等了 1 小时 30 分                                │
│    需要一个权限才能继续                                   [打开任务] │
│ ② 审批 · 是否合并 task-801 的候选 · 等了 1 小时                      │
│    宠物的理由摘要……                                       [去处理] │
│ ③ task-813 有 2 个问题等你 · 等了 45 分钟                            │
│    · 先只做第一步，还是三步一起规划？                                │
│    · 只出计划，还是接着实现？                             [打开任务] │
├───────────────────────────────┬──────────────────────────────────────┤
│ 等别人（2）                   │ 在跑什么（4）                        │
│ task-805 评审中 → task-806    │ task-811 运行中 · 已跑 12 分钟       │
│   从 09:15 开始等             │   跑过夜稳定性对比                   │
│ 飞书群 A 有 3 条待发          │   硬件：调试板 1                     │
│   最早一条等了 4 分钟         │ task-812 准备中                      │
├───────────────────────────────┴──────────────────────────────────────┤
│ 宠物这边                                                             │
│ 你最近的纠正（1）：否决“删除工作区 X”——“这个还要留着对比”            │
│ 未闭环 5 条 · 议程 3 条                              [到记录页看全部]│
├──────────────────────────────────────────────────────────────────────┤
│ ▸ 关注任务（8）  ▸ 已忽略（3）  ▸ 未关注（20）                       │
└──────────────────────────────────────────────────────────────────────┘
```

现有的关注、已忽略、未关注三个折叠列表保留在最下面，行为不变。原来的三张数字卡并进顶部状态条。“最近动态”去掉：它列的是最近的审批和关注任务，这些内容已经按“谁该动”分到上面三块里了。

### 4.2 要你定

收三类东西，同一件事只出现一次：

| 类型 | 来自哪里 | 页面上显示 |
| --- | --- | --- |
| 审批 | 宠物审批表里未处理、且不是“想法”的审批 | 标题、宠物的理由摘要、风险、关联任务；点开现有的审批详情再批准或否决 |
| 任务有问题等你 | 任务在等待状态，且它的状态卡写了等 owner 决定的事 | 把问题原文列出来 |
| 任务被阻塞 / 失败 / 上一轮没跑完 | 任务状态是阻塞或失败；或任务在等待状态，但最近一轮不是正常结束 | 最近一轮的错误信息，没有就显示状态卡的现状 |

去重规则：

- 一个任务如果已经有一条关于它的未处理审批，只显示审批，不再单列任务。
- 一个任务如果有评审在跑，归到“等别人”，不算等你。
- 正在运行的任务不看状态卡里的问题。那是上一轮写的，owner 多半已经回答了，这一轮正在处理。

排序：等得最久的排最上面，编号从 ① 开始。等得越久越可能被忘掉。最多显示 50 条，同时给出总数。

**不急的**单独折叠成一行“不急的还有 N 件”，展开后最近的排最上：

- 宠物提的想法：没有任务停在它上面。
- 上一轮正常结束、状态卡里也没有问题的任务：只是等你下一句话。显示它状态卡里的下一步。

这个“急 / 不急”的划分是 AHA 自己的：AHA 没有截止时间字段，但能确切知道“有没有东西停在这件事上”。

### 4.3 等别人

| 类型 | 来自哪里 | 页面上显示 |
| --- | --- | --- |
| 评审中 | 任务在等待状态，评审关联表里有一个还在准备或运行的评审任务 | 任务 → 评审任务编号，从什么时候开始等 |
| 审批执行中 | 审批状态是执行中（owner 已批准，后台正在做，比如删除工作区） | 审批标题和种类 |
| 渠道待发 | 渠道外发队列里有待发消息 | 渠道名、条数、最早一条等了多久 |

评审结束后，原任务会自动回到“要你定”。

AHA 目前没有“等外部的人回复”这种记录（比如等合作方答复）。这类事宠物写在未闭环清单里，页面在“宠物这边”显示清单条目，不假装能结构化。要做成独立一栏，需要宠物的清单有固定格式，列在第八节。

### 4.4 在跑什么

列出状态是运行中或准备中的任务：编号、标题、已经跑了多久、状态卡里的现状（上一轮写的“现在到哪了”）、绑定的硬件资源名称。最多 30 条。

宠物自己的任务不列在这里，它的状态在顶部状态条。

### 4.5 宠物这边

- **你最近的纠正**：owner 否决审批时写的原因。AHA 已经把它记成纠正记录并交给宠物，宠物把判断写进原则文档后这条记录关闭，7 天后也会自动消失。页面显示还没关闭的那些，让 owner 看到“我说过的话宠物还没消化”。
- **未闭环和议程**：显示宠物摘要里的前几条（未闭环 3 条、议程 2 条）和总数，全文在记录页。

### 4.6 顶部状态条

一行：巡检健康、要你定的件数、等别人的件数、在跑的个数、上次巡检时间。版本号和运行时长移到悬停提示里。渠道异常数不为 0 时在这一行显示红色标记，点击跳到渠道卡片。

第一版的状态条由服务端按数字拼出来。参考图顶部那段“人话摘要”是 Agent 写的；AHA 里可以让宠物每次巡检后写一段，放第二步做。

### 4.7 其余三个页签

审批、记录、设置第一步不动。记录页按知识类型重排放第三步。

### 5.2 本次已补的三处

都在任务分支上，只增不改，没有改表结构。

**1. 批量读取（`internal/store/pet_desk.go`）**

- `TaskStateCards`：一次读多个任务的状态卡。
- `LatestMainTurnBriefs`：一次读多个任务各自最近一轮主 Agent Turn 的状态、错误和时间。

两者都按 400 个任务一批查询，查询次数不随任务数增长。

**2. 工作台接口多返回一个 `desk` 字段（`internal/app/pet_desk.go`）**

`GET /api/v1/pet/workbench` 的返回里新增 `desk`，原有字段不变：

```
desk
├─ needs_owner[] / needs_owner_total      要你定
│    kind: approval | question | blocked | failed | stopped
│    approval_id, approval_kind, risk, task_id, task_code,
│    title, questions[], detail, since
├─ later[] / later_total                  不急的
│    kind: idea | next_step（字段同上）
├─ waiting_others[] / waiting_others_total 等别人
│    kind: review | executing | channel
│    task_id, task_code, title, on, count, since
├─ running[] / running_total              在跑什么
│    task_id, task_code, title, status, turn_status,
│    detail, hardware[], since
├─ corrections[]                          owner 的纠正
├─ open_loops[] / open_loops_total        未闭环
└─ agenda[] / agenda_total                议程
```

读取失败时 `desk` 为空，其余字段照常返回。

**3. 宠物能读到任务状态卡**

- `aha_task_detail` 的返回新增 `state_card`：现状、下一步、等 owner 决定的事、更新时间。
- `aha_pet_work_state` 的 `open_tasks` 每行新增 `owner_questions`：这个任务的状态卡里有几件事等 owner 决定。owner 没开“查看其他任务信息”权限时，不是宠物创建的任务不返回这个数。
- 两个工具的说明文字同步更新。

这一条是给宠物守漏斗用的：以前宠物只能从任务的最后一段回复里猜它在等什么，现在能直接读到任务自己列的问题，再决定是提醒 owner、自己回答，还是提成审批。

### 5.3 测量

在测试库里造了 2000 个未闭环任务（200 个运行中、600 个要 owner 处理、1200 个只等下一句话），每个任务两轮 Turn、一张状态卡：

- 汇总 `desk`：约 25–29 毫秒。
- 整个工作台接口：约 40 毫秒。

测试库关闭了磁盘同步，正式环境的读取不涉及同步写，量级应当接近，但没有在正式数据上量过。

这些本次没做，原因写在每条后面。

| 需要 | 现状 | 缺什么 |

## 八、风险和已确认的决定

- **状态卡可能过期。** 状态卡由每轮的 Agent 更新。如果某一轮失败在更新之前，卡上还是上一轮的问题。页面显示卡的更新时间，让 owner 能看出来。正在运行的任务已经不读卡上的问题。
- **“等了多久”是近似值。** 任务类条目用的是任务最后更新时间，问题类条目用状态卡更新时间。任务表没有“进入当前状态的时间”这个字段。

### 已确认的决定（owner，2026-11-26，按推荐方案）

- “要你定”按等得最久的排在最上。
- 只等下一句话的任务归到“不急的”，默认折叠。
- 第一步的页面就在这个任务的分支上做。实现交给 Opus，Main 评审；全部完成后报告 owner，由 owner 决定合并到主仓库。
- 审批条目不在概览上直接批准或否决，点开现有的审批详情再处理。删除类审批只看一行摘要就能一键批准，风险太大。

| `who` | `owner` 是 `other` 时写是谁 |
| `state` | `open`（在推进）、`waiting`（等负责方）、`blocked`（卡住）、`closed`（已闭环） |
| `step` | 走到哪一步，一句话 |
| `blocker` | 卡点，一句话，没有就空 |
| `updated_at`、`opened_at`、`closed_at` | 服务端填 |

规则：

- 任务每轮结束更新状态卡时带上当前的分线。状态卡工具（`memory_update`）加 `lines`，按 `id` 合并：新 `id` 是开线，已有 `id` 是更新，闭环要显式把 `state` 写成 `closed`。没带到的线保持原样，不当成闭环。
- 未闭环的线最多 8 条，每个文字字段最多 200 个字。
- 服务端把每条线的开、状态变化、闭环记成事件（任务、线、前后状态、哪一轮、时间），所以闭环的线不会消失，会留在时间线上。
- 没有分线的任务（老任务，或只有一件事的小任务）一切照旧。只有一件事的任务不强求分线。
- 存储：状态卡表加一列存当前分线，另加一张分线事件表。这是表结构变更，随迁移走。

提示词：任务的工作约定里，“更新任务状态卡”那一条加一句：任务里同时在走不止一件事时，把每件事记成一条线，写清谁负责、走到哪、卡在哪；闭环了就标闭环。

### 12.4 由分线推出“卡在谁”

不另加字段。任务处于等待输入且有分线时：

| 未闭环的线 | 任务卡在谁 |
| --- | --- |
| 有 `owner=self` 且 `state=open` 的线 | 不等谁：任务自己能往下走 |
| 没有上面那种，有 `owner=owner` 的线 | 等 owner |
| 只剩 `owner=other` 的线 | 等别人（列出 `who`） |
| 全部闭环 | 分线说明不了现在卡在谁，按状态卡判断 |

没有分线的任务沿用现在的规则（状态卡有问题算等 owner，否则算只等下一句话），页面上标明“没有记录分线”。分线全部闭环的任务同样按状态卡判断：任务做完几条线之后，可能只在状态卡上写了一个等 owner 决定的问题，没有再开线；只看分线会把这个问题藏起来（评审时发现，原表写的是“只等下一句话”）。

工位的分类跟着改：

- “要你定”里“有 N 个问题等你”这一类，在任务有分线时只在“等 owner”的情况下出现；显示的是负责人为 owner 的线，而不是状态卡里的全部问题。
- “等别人”新增一类：任务只剩等别人的线，显示在等谁、哪条线。

### 12.5 停着没人推

服务端算出名单，条件全部满足才算：

- 任务处于等待输入，最近一轮主 Agent Turn 正常结束；
- 按 12.4 是“不等谁”（没有分线的任务：状态卡有下一步、没有等 owner 决定的事）；
- 没有针对它的未处理审批，没有在跑的评审；
- 距最近一轮结束超过 15 分钟（常量，写明依据）；
- 没被 owner 忽略。

名单去两个地方：

- **宠物的工作状态**（`aha_pet_work_state`）新增 `stalled_tasks`，带一句固定说明：这些任务自己能往下走却停着，逐个给它发一句继续，或者说明为什么不该继续。只包含宠物创建或关注的任务，权限规则和 `open_tasks` 一致。说明文字放在返回数据里，不改宠物的唤醒提示词。
- **工位**新增一类“停着没人推”，放在“要你定”这一栏的最上面，用和审批不同的样式：任务、哪条线、停了多久，带“让它继续”按钮（给任务发一句固定的继续消息，要二次确认内容）和“打开任务”。它不计入“N 件要你定”，状态条上单独显示“N 个停着”。

### 12.6 任务详情面板

**底部一条改成：关注 / 最近活动 / 已忽略。**“未关注”换成“最近活动”（owner 已确认）：

- 列出最近有动静的任务，按最后活动时间从新到旧，包括最近 7 天内完成或取消的。现在任务一完成就从概览上消失，“今天干完了什么”看不到。
- 不含已忽略的、宠物自己的任务、系统托管项目里没被关注的任务。最多 30 条，带总数。
- 每行：编号、标题、状态、最后活动时间；没关注的带“关注”，都带“忽略”。原来“未关注”那一列的用途由它承接。

**点任何一条任务弹出生命周期。**概览上所有任务行（要你定、等别人、在跑什么、停着没人推、关注、最近活动）点标题都打开它；“打开任务”按钮照旧直接进任务页。弹窗从上到下：

1. **头**：编号、标题、项目、状态，“打开任务”。
2. **现在**：现状、下一步、卡在谁、停了多久（取自状态卡和 12.4）。
3. **分线**：一张表，未闭环的在前，每行是 线 / 谁负责 / 走到哪 / 卡点 / 更新时间；已闭环的折叠成“已闭环 N 条”。没有分线时写“这个任务没有记录分线”。
4. **系统知道的并行**：派出去的 Sub（每个在跑还是做完了）和关联的评审任务（结论）。这两样不靠任务自己记。
5. **转折点**（默认展开，时间线）：目标每次怎么变和原因、owner 定下的约束、宠物为它提的审批和 owner 的决定及原因、评审结论、分线的开和闭环、合并收尾、完成或取消。
6. **每一轮**（默认折叠）：一轮一行，时间、耗时、结果第一句；细节去任务页看对话。
7. **几个数**：创建时间、总轮数、总耗时、Token（沿用任务列表的算法）。

数据由一个新接口按需返回（owner 会话），点开时才读，不进工作台的首次加载。

### 12.7 分三步做

每一步单独派工、单独评审、单独合并，前一步合并后再做下一步。

**4A 分线和事件（后端为主）**

1. 状态卡工具和 HTTP 接口接受 `lines`，按 `id` 合并；超出条数或字数上限时拒绝并说明。
2. 分线的开、变、闭环都有事件；同一轮里重复提交相同内容不产生重复事件。
3. 任务提示词加上记分线的要求；提示词相关的现有测试同步更新；顺序断言要先断言锚点存在。
4. 下一轮的提示词里能看到上一轮留下的分线（和状态卡其余部分一起）。
5. 迁移可重复执行；有故障注入测试证明迁移中途失败能回滚重试。
6. Task 页面的状态卡显示分线。

**4B 停着没人推**

7. 名单的五个条件各有用例，包括正好 15 分钟的边界、有审批、有评审、被忽略、没有分线的任务。
8. `aha_pet_work_state` 返回 `stalled_tasks` 和说明；未开查看任务权限时不泄露非宠物创建任务的详情；默认 16KB 预算下这份名单不被裁掉。
9. 工位显示“停着没人推”，不计入“要你定”的件数；“让它继续”发出的消息内容固定、可见、要确认；发出后这条从名单消失。
10. 12.4 的分类表逐行有用例；没有分线的任务行为不变。

**4C 最近活动列和生命周期弹窗**

11. 底部是关注 / 最近活动 / 已忽略；最近活动包含 7 天内完成的任务；关注和忽略按钮可用。
12. 概览上每一类任务行点标题都能打开弹窗；“打开任务”仍直接进任务页。
13. 弹窗七块齐全；没有分线、没有审批、没有评审、没有 Sub 的任务各块有空状态；任务不存在或已删除时有提示。
14. 时间线按时间排序，各类事件的来源能对上（目标事件、约束、审批、评审、分线事件、Turn）。
15. 弹窗内容超出时在弹窗内滚动，打开弹窗不让概览出现整页滚动；键盘可关闭，焦点回到触发的那一行。

**通用**：服务端文字转义；中英文文案齐全；首屏体积按 `build.test.mjs` 的惯例处理；接口和路由有增减时更新宠物接口覆盖台账；前端构建、单测、浏览器用例和相关 Go 用例通过。

**后端实现记录**

- 工位、宠物工作状态和生命周期共用分线判定。等了正好 15 分钟仍在宽限期。工位按批读取最近结束时间。待处理和执行中的审批都挡住“停着没人推”，包括审批列表上限之外的记录。
- 最近活动取任务更新时间和任一 Agent 最近一次 Turn 结束时间中的较晚值。完成、取消任务保留到满 7 天。宠物默认预算优先保留全部停滞记录，其他任务的详情仍按查看权限遮蔽。
- 生命周期请求到达后才读取各来源。时间相同的事件按固定来源顺序排列，同一来源保留写入顺序。评审使用关联评审任务的有效 verdict 和持久保存的完成决定。轮数和耗时统计主 Agent 全部 Turn，Token 复用任务列表算法。
- 评审时改了四处（Main 改的）：分线全部闭环的任务改按状态卡判断，避免状态卡上的问题被藏进“不急的”，这类任务停下来时也进“停着没人推”；最近一轮没正常结束的任务不再被分线规则盖住，照旧显示为“这一轮没跑完”；时间线补上完成和取消；每一轮的摘要跳过结果开头的空行。`idle_since` 保持实现时的含义（只在停着没人推时有值），约定里补了说明。
- 联调时改了三处（Main 改的）：分线事件原来只给一段拼好的文字，里面是 `self`、`waiting` 这样的英文取值，中文界面上直接露出来，改成另带结构化的 `line`，由页面按语言显示；时间线补上完成、取消的文案，评审结论（`APPROVE`、`REQUEST_CHANGES`、`required`、`skipped`）换成可读的说法；目标变更的新目标和原因分两行显示。用真实二进制加测试库起服务，在真实页面上走过一遍：停着没人推的显示和“让它继续”（发出的是那句固定的话，服务端返回 202，这条随后从名单消失）、按分线显示的条目、等别人的线、最近活动、生命周期弹窗（打开、内容、Escape 关闭后焦点回到原行、弹窗打开前后整页都不滚动）。页面是英文界面，中文界面没有在这台机器上看过。
- 用定向 Go 测试验证分类、边界、权限、响应预算、生命周期时间线和截断。200 轮 Turn、100 条分线事件、20 次目标变更的本机 SQLite 夹具上，发起 20 次已登录 HTTP 请求并解码 JSON，P50 为 3.52 ms，P95 为 4.12 ms。 `go vet`、store、domain、httpapi 整包和覆盖台账检查通过。app 整包只有在 `71b9cac` 已复现的三个失败。

### 12.8 风险和没定的事

- **靠任务如实填。**分线填得不准或忘了更新，“卡在谁”和“停着没人推”就跟着不准。页面显示每条线的更新时间；任务处于等待输入而分线超过一轮没更新时标出来。
- **提示词改动影响所有任务。**每轮多写几行，成本很小，但所有项目的任务行为都会变，4A 合并后要观察几天。
- **老任务没有分线。**它们沿用旧规则，弹窗里只有时间线。
- **“让它继续”是 owner 替任务做的推动**，消息内容固定，不带新指令，避免变成一个随手发指令的入口。
- **没定**：任务有不依赖别人的下一步时，是否不许它结束这一轮。这涉及任务何时可以收工，影响面比分线大，owner 还没决定，这一步不做。

### 12.9 4B、4C 的接口约定

4A 已合入 main（`837682f`）。剩下两部分都要改同一批文件，所以改成按前后端切：一边做全部后端，一边做全部前端，同时进行，靠这一节的约定对上。字段名以这里为准；实现中发现约定不够用，后端可以只增不改地加字段并在交付说明里写明，不能改名或删字段。时间一律 RFC 3339，没有值时是 Go 的零值时间，前端按“没有”处理。

**卡在谁（`stuck_on`）**：只对等待输入的任务计算，取值：

| 值 | 条件 |
| --- | --- |
| `self` | 有 `owner=self` 且 `state=open` 的未闭环分线 |
| `owner` | 不满足上一条，且有 `owner=owner` 的未闭环分线 |
| `other` | 不满足上两条，且有 `owner=other` 的未闭环分线 |
| `none` | 有分线记录，但没有上面三种线（全部闭环，或只剩自己暂停、受阻的线） |
| `unknown` | 任务没有记录过分线，沿用旧规则 |

“有分线记录”指状态卡上有分线（含已闭环的）。`owner=self` 但 `state` 是 `waiting` 或 `blocked` 的线不算“自己能推”：`waiting` 说明它在等别的线，`blocked` 说明有卡点，这两种都归到 `owner`、`other` 或 `none` 里看其余的线；如果只剩这种线，按 `none` 处理。

**工作台接口 `GET /api/v1/pet/workbench` 的 `desk` 新增或变化：**

```
desk
├─ stalled[] / stalled_total            停着没人推（最多 30 条，停得最久的在前）
│    task_id, task_code, title,
│    line_id, line_title,               自己能推的那条线；没有分线的任务为空
│    detail,                            那条线的 step；没有分线时是状态卡的第一条下一步
│    since                              最近一轮主 Agent Turn 结束的时间
├─ recent[] / recent_total              最近活动（最多 30 条，最新的在前）
│    task_id, task_code, title, status,
│    watched,                           是否已关注
│    last_active                        任务最后活动时间
├─ needs_owner[] / later[] 每条新增
│    stuck_on,                          任务类条目才有，取值见上表
│    lines[]                            kind=question 且 stuck_on=owner 时，负责人是 owner 的未闭环线：
│                                       id, title, state, step, blocker
└─ waiting_others[] 新增一种 kind=line  任务只剩等别人的线
     task_id, task_code, title,
     on,                                等的是谁，多个用顿号连接
     lines[],                           同上结构，负责人是 other 的未闭环线，另带 who
     since                              任务最后更新时间
```

分类规则的变化（只影响等待输入的任务，其余不变）：

- `stuck_on=self`：满足 12.5 其余条件的进 `stalled`，不再进 `needs_owner` 或 `later`；还没停够 15 分钟的进 `later`（kind 仍是 `next_step`）。
- `stuck_on=owner`：进 `needs_owner`，kind 是 `question`，带 `lines`；状态卡里的 `questions` 照常带上。
- `stuck_on=other`：进 `waiting_others`，kind 是 `line`。
- `stuck_on=none`：按状态卡判断，和 `unknown` 一样——状态卡有等 owner 决定的事进 `needs_owner`（kind 是 `question`，不带 `lines`），否则进 `later`。分线全部闭环、状态卡有下一步、没有等 owner 决定的事，并且满足 12.5 其余条件的进 `stalled`；还留着自己暂停或受阻的线的不进 `stalled`，那是任务写明了的等待理由。
- `stuck_on=unknown`：和现在一样（有问题进 `needs_owner`，否则进 `later`）；另外满足“状态卡有下一步、没有等 owner 决定的事”和 12.5 其余条件的进 `stalled`。
- 最近一轮主 Agent Turn 不是正常结束的（中断、失败），除了 `stuck_on=owner` 以外都不按分线分类，照原规则进 `needs_owner`（kind 是 `stopped`，状态卡有问题时是 `question`）：分线是这一轮出事之前写的，owner 需要先知道它没跑完。
- 有未处理审批、有在跑的评审、被忽略的任务，规则和现在一样，优先于上面各条。

`recent` 的范围：非宠物任务、未被忽略；系统托管项目里的任务只有被关注时才出现；状态是完成或取消的只保留最近 7 天内的；草稿不出现。`last_active` 取任务更新时间和最近一轮 Turn 结束时间中较晚的。

**宠物工作状态 `aha_pet_work_state` 新增：**

```
stalled_tasks[]        id, code, title, line_id, line_title, detail, idle_minutes
stalled_tasks_note     固定说明文字，名单为空时不返回
```

只包含宠物创建或关注的任务；未开“查看其他任务信息”权限时，不是宠物创建的任务只返回 `id`、`code` 和 `idle_minutes`。默认 16KB 预算裁剪时这份名单的每一行都保留。

**新接口 `GET /api/v1/tasks/{id}/lifecycle`**（owner 会话；任务不存在返回 404）：

**“让它继续”**不新增接口：前端用现有的发消息接口给任务发一句固定的话，内容在确认框里原样显示。中文是“继续：按状态卡上的下一步往下做；做不了就说明卡在哪。”英文是对应的翻译，随界面语言。

**页面**（前端按这个做）：

- 状态条在“N 件要你定”后面加“N 个停着”，为 0 时不显示。
- “要你定”这一栏最上面是“停着没人推”，和审批、任务条目用不同的底色区分，不编序号；每条显示任务、哪条线、停了多久、`detail`，按钮是“让它继续”和“打开任务”。
- `kind=question` 且带 `lines` 时，显示这些线（标题、走到哪、卡点），不再列状态卡的全部问题；`stuck_on=unknown` 的任务条目在小字里标“没有记录分线”。
- “等别人”里 `kind=line` 显示任务、等谁、哪几条线。
- 底部三列是关注 / 最近活动 / 已忽略。最近活动每行：编号、标题、状态、最后活动时间；没关注的带“关注”，都带“忽略”；已完成或取消的行用弱化样式。原来的“未关注”一列不再出现。
- 概览上所有任务行（要你定、不急的、等别人、在跑什么、停着没人推、关注、最近活动、已忽略）点标题打开生命周期弹窗；原来的“打开任务”按钮保留。审批和想法行点标题仍是审批详情。
- 弹窗七块按 12.6 的顺序。读取中、读取失败、任务不存在各有状态；旧服务端没有这个接口（404）时提示不可用并给“打开任务”。
