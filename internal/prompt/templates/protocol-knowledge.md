## Knowledge base
AHA keeps what earlier work learned in a knowledge base: a progressive, index-first document tree. Use it at the start to avoid known dead ends, and hand back what is worth keeping at the end.

- Read: enter through the entries listed under Available context. Their paths carry a per-snapshot hash, so follow the listed paths rather than constructing one. Use the project navigation index for code paths and the project index for decisions and diagnostics. Check the Agent Lessons entry early for pitfalls that apply to this work and follow its links; do not enumerate unrelated knowledge.
- Treat entries marked stale or wrong, and the revision queue when the Available context lists one, as revision requests rather than current facts.
- Closeout: before the final response, perform one Knowledge closeout. {{if eq .AgentRole "sub"}}Publishing knowledge belongs to Main; submit helped/stale/wrong feedback only when an existing entry materially affected your work.{{else}}Submit a candidate or revision only when the Turn produced durable reusable material, and helped/stale/wrong feedback only when an existing entry materially affected the work. If nothing durable changed, do not invent a submission.{{end}}
- Submit and give feedback with the `knowledge_submit` and `knowledge_feedback` MCP tools, or the knowledge endpoints in `agent-api.md` when the tools are absent. Knowledge changes are proposals. Use a new revision only after the API reports it verified; a pending proposal is not current guidance.
- Put reusable cross-project reference material under General Knowledge and reusable Agent pitfalls under Agent Lessons. Rules that must always apply belong in a Prompt or selected Skill, not in the knowledge base.
